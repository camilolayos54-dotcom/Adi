### 3. Matriz de Restricciones No Funcionales (NFRs) (De D2)

| ID NFR | Categoría | Meta Mensurable | Estrategia de Arquitectura |
| --- | --- | --- | --- |
| **NFR-01** | Rendimiento y Latencia | Tiempo de respuesta en consultas de inventario < 100 ms | Indexación relacional en BD (SKU, Marca, Modelo, Talla, Color) y consultas optimizadas |
| **NFR-02** | Consistencia y Concurrencia | Erradicación total (0%) de descuadres o ventas sobre agotados | Transacciones atómicas ACID con bloqueos optimistas/pesimistas en operaciones de existencias |
| **NFR-03** | Ingesta por Lote | Procesamiento e indexación de lotes (50+ pares con fotos) < 3 segundos | Pipeline asíncrono de optimización de imágenes (WebP) e inserción masiva (bulk insert) |
| **NFR-04** | Seguridad y Privacidad | Cifrado de datos de costos de importación y autenticación segura | JWT con hashing de contraseñas bcrypt/Argon2 y variables de entorno protegidas |
| **NFR-05** | Responsividad y Acceso | Operatividad 100% en pantallas de escritorio y smartphones | Diseño responsive CSS/Web, empaquetamiento Docker y despliegue Cloud |

### 4. Arquitectura de Stack Tecnológico (ADR Oficial) (De D3)

| Capa Tecnológica | Selección Oficial | Justificación NFR / Equipo | Alternativas Rechazadas (ADR) |
| --- | --- | --- | --- |
| **Backend API** | Node.js (TypeScript) / Python (FastAPI) | Cumple NFR-01/03. Agilidad en APIs RESTful, tipado estricto y manejo fluido de modelos relacionales | **PHP Tradicional / Ruby:** Rechazados por menor flexibilidad en arquitecturas desacopladas modernas |
| **Base de Datos** | PostgreSQL / SQLite | Cumple NFR-02. Integridad referencial estricta, bloqueos ACID y rendimiento relacional | **MongoDB / NoSQL:** Rechazado. El inventario de variantes de tenis exige consistencia relacional estricta, no eventual |
| **Frontend Gestor** | JavaScript (React / Vue / Standards) | Cumple NFR-05. Interfaz de administración responsiva, modular y de alta velocidad | **Frameworks Múltiples Pesados:** Rechazados para evitar sobreingeniería en el panel administrativo interno |
| **Almacenamiento** | Cloud Storage + CDN (WebP) | Cumple NFR-03. Optimización automatizada de imágenes reduciendo el peso de transferencia | **Almacenamiento Local en Servidor:** Rechazado para evitar acoplamiento de archivos al contenedor Backend |
| **Despliegue MVP** | Docker + Hosting Cloud (Render/Railway) | Despliegue contenedorizado, reproducible y económico (<$15 USD/mes) | **Servidores Dedicados Complejos:** Sobreasignación presupuestal innecesaria para la etapa de MVP |

- **Suite de Herramientas:** VS Code, Git/GitHub, Docker Compose, Postman/Thunder Client, GitHub Actions (CI/CD) y Sentry.

### 7. Estrategia de Pruebas y Criterios DoD/DoR (De D8 & D9)

#### A. Pirámide de Pruebas
| Nivel | Componentes a Probar | Herramienta | Cobertura Mínima |
| --- | --- | --- | --- |
| **Unitarias** | Reglas de variantes, SKU, cálculo de existencias y colillas | Jest / Vitest / PyTest | **> 80% de lógica de negocio** |
| **Integración** | Endpoints HTTP REST (CRUD Catálogo, Bulk Ingest, Stock) | Supertest / Postman | **100% de endpoints críticos** |
| **Carga / Concurrencia** | Actualización simultánea de stock y filtrado masivo | K6 / Artillery | **50 peticiones/s (<100 ms)** |
| **UAT (Aceptación)** | Flujo de ingesta por lote y colillas por el Operador | Manual / Playwright | **100% de aprobación del Operador** |

#### B. Governance DoD y DoR
- **Definition of Ready (DoR):** Requisito con objetivo acotado al Gestor, criterios de aceptación cuantitativos y modelo relacional definido.
- **Definition of Done (DoD):** Código verificado por linter, pruebas unitarias e integración al 100%, PR aprobado por Tech Lead y despliegue exitoso en Staging.
