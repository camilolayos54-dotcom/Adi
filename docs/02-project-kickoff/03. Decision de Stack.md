### 2. Stack Tecnológico Oficial (Architecture Decision Record)

| Capa | Tecnología Elegida | Justificación NFR / Decisión de Equipo | Rechazos (Por qué NO otras opciones) |
| --- | --- | --- | --- |
| **Backend API** | Node.js (TypeScript) / Python (FastAPI) | Alta agilidad de desarrollo, tipado estricto, excelente rendimiento en APIs RESTful y manejo transparente de JSON relacional para variantes de calzado. | **PHP Tradicional / Ruby:** Rechazados por menor flexibilidad en ecosistemas modernos de desarrollo desacoplado. |
| **Base de Datos** | PostgreSQL / SQLite | Garantiza consistencia ACID estricta (NFR-02) para evitar descuadres de stock, soporte nativo de tipos de datos relacionales e indexación avanzada. | **NoSQL (MongoDB):** Rechazado. El inventario de calzado por SKUs, tallas, colores y colillas requiere integridad relacional estricta, no eventual. |
| **Frontend Gestor** | JavaScript (React / Vue / Web Standards) | Permite construir una interfaz intuitiva, responsiva (NFR-05) y de alta velocidad para la catalogación por lote y emisión de comprobantes. | **Frameworks Múltiples Pesados:** Rechazados para evitar sobreingeniería innecesaria en el panel administrativo. |
| **Almacenamiento de Medios** | CDN / Cloud Storage con compresión WebP | Optimización automatizada de imágenes de calzado (NFR-03) reduciendo el peso de almacenamiento. | **Almacenamiento Local en Servidor:** Rechazado para evitar acoplamiento de archivos al contenedor del backend. |
| **Despliegue MVP** | Docker + Cloud Hosting (Render / Railway / VPS) | Despliegue contenedorizado, reproducible y económico (<$15 USD/mes) para la versión `v0.1.0-alpha`. | **Servidores Dedicados Complejos:** Sobreasignación presupuestal innecesaria para el arranque del MVP. |

### 3. Implicación de Compuerta
- **Condición:** Proceed. El stack tecnológico responde directamente a las restricciones del proyecto Adi y a las fortalezas del equipo.
